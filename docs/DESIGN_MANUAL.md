# 程园小二业务与产品设计手册

版本：v0.1

更新日期：2026年10月13日

状态：业务与产品方案，供部门讨论和后续开发使用

本手册明确程园小二新入口的建设目标、首期范围和办理规则。首期由学生小程序承接反馈提交与结果查询，由权益生活部使用网页后台维护办理过程。拟咨询审核和最终回复审核纳入后台，打印盖章、线下咨询、部门邮件回复继续沿用现行工作方式。

本手册描述目标方案，不表示相关能力已经实现。具体页面交互、接口、数据字段和部署配置由后续技术设计确定。

## 1 项目背景与建设目标

### 1.1 现行工作方式

学校权益生活部通过程园小二接收同学对学校的意见、建议和问题反馈。收到反馈后，权益成员联系同学或实地调查，整理拟咨询材料，交负责人审核，打印盖章，再携材料向对应部门的分管老师咨询。相关部门通过权益工作小组邮箱回复，权益成员整理结果后反馈给同学，并完成内部汇报和月报记录。

当前主要在受理和获得最终结果时向同学发送短信。调查、准备材料、提交咨询和等待回复期间，同学较难了解办理进展。当前反馈量约为每周两条，开发和日常维护的投入应与这一规模相适应。

### 1.2 两个建设目标

**近期目标是改善办理追踪。** 新入口覆盖提交、办理、必要的材料补充和最终反馈，让同学知道反馈是否被接收、是否已提交相关部门，以及最终结果是否可以查看。

**后续目标是逐步降低内部工作和协调成本。** 首期稳定后，先根据实际负担考虑拟咨询材料生成、月报整理等辅助能力，再尝试跨部门线上协作。全面线上化需要多个部门共同认可接收、回复和办理方式，暂不作为首期前提。

### 1.3 投入原则

- 记录应结合实际办理动作完成，避免重复填写相同信息。
- 学生侧保持少量清晰节点，内部审核、盖章和日常跟进不逐一增加学生状态。
- 办理过程和结果应真实表达；收到解释、提出整改计划和问题实际解决，需要在最终回复中说明。
- 先通过试用检验流程和工作负担，再决定后续投入。

## 2 建设范围与开发分期

### 2.1 首期范围

| 部分 | 首期能力 |
| --- | --- |
| 学生小程序 | 提交反馈、查看本人反馈与办理节点、按要求补充材料、查看最终回复、简单满意度评价 |
| 网页后台 | 接收和办理反馈、成员接手、请求补充材料、拟咨询审核、最终回复审核、说明原因后关闭、内部留档和经办记录 |
| 后台账号 | 专门的工作人员账号体系，固定区分经办、负责人审核和账号管理权限，再按功能区授权 |
| 基础统计 | 反馈数量、各办理节点数量和简单评价统计 |
| 使用安排 | 独立自建账号用于测试和小范围试用；接通真实学校 CAS 后正式上线；服务限定校园网访问 |

首期的小程序用于学生办理入口，工作人员使用独立网页后台。相关部门老师继续通过线下咨询和邮件参与，首期无需部门老师登录后台完成回复。

### 2.2 后续范围

首期稳定后，优先评估拟咨询材料生成、月报数据整理与导出等内部辅助能力，再根据实际协调条件尝试一个部门的线上接收和回复。

以下能力保留为后续方向：

- 精选公开案例。首期不启用公开案例，不将任何反馈自动对其他同学公开。
- 自动月报和更完整的统计报表。
- 提交给部门后再次请求学生补充材料。
- 独立的学生消息回复功能区。首期考虑功能区授权的扩展方向，不实施该功能本身。
- 跨部门线上协作及更广泛推广。

新增消息推送暂不列为首期承诺。首期以学生能主动查看办理进展和最终结果为基础，提醒渠道另行评估。

## 3 业务流程与职责

### 3.1 学生看到的四个主节点

```text
已提交反馈 → 权益部门已接收 → 已提交相关部门 → 已反馈最终结果
```

| 节点 | 含义与更新依据 |
| --- | --- |
| 已提交反馈 | 系统已保存反馈，并生成可供本人查询的记录 |
| 权益部门已接收 | 权益成员已接收并开始办理；了解情况、拟咨询编写及其审核、打印盖章都归入此阶段 |
| 已提交相关部门 | 拟咨询材料已实际送达或已完成对相关部门的咨询，等待部门回复 |
| 已反馈最终结果 | 最终回复已通过负责人审核并向提交人发布，学生可以查看结果 |

学生侧不单独设置拟咨询待审核、已盖章、收到邮件但尚未反馈等节点。内部审核记录和邮件留档不自动推进学生状态。

### 3.2 权益部门的实际办理过程

1. **接收和了解情况。** 经办人接收反馈，通过联系同学、查看材料或实地调查了解问题。
2. **编写拟咨询并送审。** 经办人在后台提交拟咨询材料，由负责人在线审核；审核不通过时返回经办人修改，学生侧保持原阶段。
3. **打印盖章并咨询。** 审核通过后，按现行要求打印盖章并联系相关部门。材料实际送达或完成咨询后，更新为已提交相关部门，建议上传盖章后的拟咨询文件。
4. **等待和跟进回复。** 继续按现行方式跟进。老师的邮件由权益成员收集和整理，后台记录回复来源及实际录入人，不将代录描述为老师在系统内操作。
5. **整理最终回复并送审。** 经办人整理供学生阅读的最终回复，由负责人在线审核。建议上传收到的邮件文件或截图，审核不通过时继续修改。
6. **发布结果并结束办理。** 最终回复通过审核后发布给学生，更新为已反馈最终结果，结束本次办理，并按现行方式完成内部汇报和月报记录。

最终回复应说明部门意见、当前解决情况及已明确的后续安排。解释原因或提出后续整改计划，也可以构成本次最终反馈；已反馈节点表示本次反馈闭环完成，不直接等同于问题已经解决。

### 3.3 补充材料分支

首期只在提交给相关部门前请求补充材料。权益成员应说明需要补充什么，学生在本人反馈中查看要求并提交补充内容，之后继续原办理过程。

待补充是办理分支，不代表已提交相关部门或已结束办理。补充动作应保留记录，且不越过拟咨询审核和实际咨询。提交给部门后的补充能力作为后续扩展。

### 3.4 关闭分支

对于重复反馈、超出受理范围或长期无法取得必要材料等无法继续办理的情况，授权经办人可以说明原因后关闭，学生可查看关闭原因，内部保留经办记录。

关闭与已反馈最终结果分别表达，统计时分别计算。首期不要求复杂的重复诉求合并，也不按固定期限自动关闭。

## 4 账号权限与成员协作

### 4.1 后台账号与功能区

后台建立专门的工作人员账号体系。账号按经办、负责人审核、账号管理三类固定权限区分职责，再配置其可访问的功能区。首期功能区为程园小二处理，未来学生消息回复作为独立功能区。

权限应同时支持按职责组合和按功能区授权，不扩展为逐条反馈授权或复杂的自定义权限体系。

| 权限类别 | 职责范围 |
| --- | --- |
| 经办 | 查看授权功能区的反馈、接收和接手、维护办理记录、请求补充材料、整理送审材料和最终回复、留档及说明原因后关闭 |
| 负责人审核 | 在授权功能区审核拟咨询及最终回复，对需修改的内容提出意见 |
| 账号管理 | 管理工作人员账号、启停账号及配置职责和功能区权限 |

后台权限由账号管理者配置，不通过学生登录或学生自行选择身份获得。

### 4.2 成员接手与经办记录

获得程园小二经办权限的成员可以查看该功能区的反馈并自由接手，无需负责人逐条分配。每条反馈区分当前经办人和历史操作人，成员接手后保留原有记录。

工作人员使用各自的账号。系统自动记录接收、交接、办理节点更新、材料送审与审核、最终发布、关闭和留档补传等操作的账号、时间及操作内容。交接本身不要求改变学生看到的办理节点。

历史记录应能解释谁在什么时间完成了什么操作。更正内容时保留必要的更正记录，避免以覆盖历史的方式丢失办理依据。

## 5 产品功能结构

### 5.1 学生小程序

- **反馈提交：** 提交问题描述、分类、地点及办理所需材料，提交成功后获得本人可查询的反馈记录。
- **我的反馈：** 查看本人记录、当前主节点及必要说明。
- **材料补充：** 查看经办人提出的补充要求，并向对应反馈补充内容。
- **最终回复：** 查看负责人审核后发布的回复，或无法继续办理时的关闭原因。
- **简单评价：** 在最终反馈后表达满意度，沿用满意、一般、不满意等简单选项。

学生只查看本人反馈。首期不启用公开案例，也不展示当前经办人、历史操作账号、内部审批意见和留档凭据。

### 5.2 网页后台

- **反馈列表和详情：** 查找反馈，查看材料、当前经办人和历史记录。
- **办理操作：** 接收、接手、提交给部门、请求补充、录入部门回复、送审及说明原因后关闭。
- **负责人审核：** 查看待审核拟咨询和最终回复，审核通过或提出修改意见。
- **内部留档：** 添加或补传拟咨询文件、邮件文件、截图等凭据。
- **基础统计：** 查看反馈数量、各办理节点数量及简单评价情况。
- **账号管理：** 管理工作人员账号及其职责和功能区权限。

基础统计服务于了解工作量和反馈情况。已反馈数量与已关闭数量应区分；已反馈数量不作为实际解决问题数量，统计应明确自身口径。

## 6 信息记录与展示边界

### 6.1 信息分层

| 信息 | 学生侧 | 内部后台 |
| --- | --- | --- |
| 本人提交内容及补充材料 | 本人可查看 | 授权人员可查看 |
| 四个主节点及必要说明 | 本人可查看 | 授权人员可维护 |
| 最终回复或关闭原因 | 本人可查看 | 授权人员按流程维护 |
| 当前经办人及历史操作账号 | 不展示 | 留经办和交接记录 |
| 拟咨询审核、最终回复审核意见 | 不直接展示 | 留内部审核记录 |
| 盖章拟咨询、原始邮件及内部截图 | 不展示 | 作为内部凭据保存 |

向学生发布的最终回复是单独整理并审核后的内容，不直接展示原始邮件及其附件。显示、下载和接口返回均需遵守信息可见范围，不能仅靠页面隐藏内部材料。

### 6.2 留档规则

系统在提交给部门时增加建议上传盖章拟咨询文件的语句，在整理最终回复时增加建议上传邮件文件或截图的语句。留档建议属于后台提示，不发送额外消息，也不作为操作必填条件。

没有凭据时允许继续办理，之后可补传并留下记录。内部文件留档与学生提交材料分别设计，具体格式、容量及保存方式在后续技术设计中确定。

### 6.3 身份与访问范围

测试和小范围试用使用独立自建账号，分别识别提交人与工作人员，避免多人共用一个学生身份。测试数据与正式使用数据分开，测试记录不计入正式统计。

正式上线须接通真实学校 CAS，以核验学生身份。校园网限制是访问边界，不能代替身份核验；学生提交和查询、网页后台及其文件访问均需在该边界内设计。

后台工作人员继续使用专门的账号和功能区权限管理。具体 CAS 对接、小程序可访问的服务地址和校园网部署方式，在正式上线前通过技术联调验证。

## 7 试用验收与后续投入

### 7.1 开发和切换顺序

1. 按本手册完成学生小程序与网页后台的首期流程，包括账号、两处审核和内部记录。
2. 使用自建账号完成测试和小范围试用，检验办理流程和更新负担。
3. 接通真实 CAS，验证校园网访问边界及学生和后台的实际可用性，再正式上线。
4. 正式切换时，新入口仅接收切换后的新反馈。旧反馈继续按旧方式处理至结束，不迁入新系统；旧历史按原归档方式保留。
5. 首期稳定后，按实际重复劳动和使用效果选择内部辅助能力，再评估跨部门线上协作。

### 7.2 首期验收场景

| 场景 | 验收重点 |
| --- | --- |
| 正常办理 | 学生提交后能查看四个主节点；经办人可录入老师的邮件回复，经负责人审核后发布最终结果，无需老师登录 |
| 补充材料 | 提交给部门前可以说明补充要求，学生能补充且记录保留，后续仍经过必要审核和实际咨询 |
| 审核退回 | 拟咨询及最终回复可分别被退回修改；审核期间学生保持原主节点，未通过的最终回复不向学生发布 |
| 成员交接 | 授权成员可接手，当前经办人与历史记录清楚，交接不增加学生节点 |
| 说明原因后关闭 | 学生能查看原因，内部保留操作记录，统计与已反馈结果区分 |
| 凭据与信息隔离 | 不上传凭据也能办理，补传留下记录；学生不能通过页面、接口或文件地址取得内部凭据和经办信息 |
| 账号与上线边界 | 学生只能查询本人反馈；后台受职责和功能区约束；正式上线前完成真实 CAS 及校园网访问验证 |

### 7.3 使用效果与维护安排

试用和上线初期重点观察：同学是否能理解目前进展和最终结果；工作人员是否愿意及时更新、是否需要重复录入；经办记录是否有助于成员接手；系统能否持续维护。

当前反馈量较小，应结合实际案例和使用意见判断效果，记录必要的更新耗时和维护问题，避免仅凭少量满意度数据决定下一阶段投入。

首期暂由开发者持有和维护系统，负责测试环境、后台账号与技术维护。维护资料应包括环境和配置说明、账号管理方式、数据备份与恢复安排，以及故障处理入口，便于后续接管。何时转为部门持有，结合实际维护条件另行安排。

### 7.4 与现有文档和代码的关系

本手册依据项目负责人确认的方案，并参考现行《权益工作小组流程》和《附件2：拟咨询内容》。这些外部流程资料未随本手册复制入库。

[原需求文档](../REQUIREMENTS.md)和[后端设计文档](../backend/DESIGN.md)保留作为既有方案及实现参考。其涉及的小程序内管理端、员工与部门角色、公开案例及迭代安排，不应直接视为本手册的首期目标。

后续开发需重点核对以下差异：

- 现有小程序管理页面与旧网页原型，如何承接新的独立网页后台。
- 现有员工、部门及学校身份模型，如何对应专门后台账号和三类功能区权限。
- 现有办理状态及部门回复路径，如何支持权益成员代录线下咨询和邮件回复，以及两处内部审核。
- 现有审核通过、办结和公开之间的关系，如何支持不公开也能向本人反馈最终结果。
- 现有附件和时间线数据，如何区分学生材料、内部凭据与学生可见信息。
- 学校认证仍为开发模拟的部分，如何替换为真实 CAS 并完成正式环境联调。

接口、数据结构和兼容安排由后续技术设计补充。本次文档更新不声明这些差异已经通过代码改造完成。
